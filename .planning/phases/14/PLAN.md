# Phase 14: MCP 2 - Plan

## Goal

The MCP server speaks protocol 2026-07-28, so Claude Code no longer has to fall back to the older `initialize` handshake. A client that opens with `server/discover` and names 2026-07-28 on each request gets the three tools and their results without ever sending `initialize`, and a client that still opens with `initialize` is served exactly as today.

## Must be true when done

- A `server/discover` request, with `_meta` naming 2026-07-28 or with no `_meta` at all, is answered with `resultType` `"complete"`, `supportedVersions` exactly `["2026-07-28"]`, `capabilities.tools` an object, `_meta["io.modelcontextprotocol/serverInfo"]` holding `name` `terminus` and the crate version, `ttlMs` `0`, `cacheScope` `"private"`, and no `instructions` key (AC1).
- Every result the server sends, `initialize`, `ping`, `tools/list`, `tools/call` and `server/discover`, carries `resultType` `"complete"` and `_meta["io.modelcontextprotocol/serverInfo"]`, and `tools/list` carries `ttlMs` `0` and `cacheScope` `"private"` beside the three tools in their fixed order, whether or not the request carried `_meta` (AC2).
- A request whose `_meta` names any version other than 2026-07-28, for `server/discover`, `tools/list` and `tools/call` alike, is refused with error `-32022` whose `data.supported` is `["2026-07-28"]` and whose `data.requested` echoes what was asked (AC3).
- `initialize` asking for 2026-07-28 is still answered 2025-06-18, each of the four legacy revisions is still echoed, 2026-07-28 is not in `PROTOCOL_VERSIONS`, and a `tools/list` with no `_meta` and no prior `initialize` still gets the tool list (AC4).
- A spawned `terminus mcp` over a fixture store, fed `server/discover`, `tools/list` and one `tools/call` per tool, each carrying 2026-07-28 `_meta` and with no `initialize` anywhere, answers every request with a result and exits 0 at EOF (AC5).
- `claude -p` on Claude Code 2.1.302, with `--debug mcp --strict-mcp-config --mcp-config` pointing at the built binary, leaves a debug log under `~/.claude/debug/` showing the server on 2026-07-28 with no fallback to `initialize`, the three tools listed, and a result from each tool (AC6, human-verify: needs a live Claude Code session).
- `docs/design/0006-recall-through-mcp.md` has a `server/discover` section and names `resultType`, `ttlMs`, `cacheScope` and `-32022`; its `initialize` section and figure 1 no longer present `initialize` as the only handshake; `CHANGELOG.md` `[Unreleased]` has an Added entry naming 2026-07-28; and the PR body carries `Fixes #45` (AC7).

## Context

### Task 2: Serve the 2026-07-28 era: `server/discover` and the `-32022` refusal

- **Files:** crates/terminus/src/cmd/mcp/mod.rs (`answer`, `initialize`, the doc comment on `PROTOCOL_VERSIONS`), crates/terminus/src/cmd/mcp/rpc.rs (`code`, `failure`)
- **Action:** Classify each request's era from `params._meta` and nothing else (D-01, D-03): a request whose `params._meta` carries the key `io.modelcontextprotocol/protocolVersion` is modern; one without it is legacy and is served exactly as today, with no check that an `initialize` came first, because refusing a `_meta`-less request would break any client or test that sends `tools/list` before `initialize`. `Request.params` is `Value::Null` when the message carried none, so `params.get("_meta")` already reads as absent without a branch. `initialize` is the legacy opening and is never put through the version check, whatever its `_meta` holds (D-01, D-08). For every other request that is modern, the value must be the string `2026-07-28`; any other value, `server/discover` included and `ping` included, is refused before the method runs with a JSON-RPC error whose code is `-32022` and whose `data` is `{"supported":["2026-07-28"],"requested":<the value as sent>}` (D-07). Add the code to `rpc::code` as the one new error code this server emits, documented there the way the four standard codes are, and give `rpc.rs` a way to build an error envelope that carries `data`; `rpc::failure` has no `data` member today and the three existing error paths keep sending none. `-32020` and `-32021` are never sent. A notification is still never answered, whatever its `_meta` says, because `rpc::parse` has already classified it before the era is read (D-09). Add the method `server/discover` to `answer`, answered whether or not the request carries `_meta` (D-04): its result is `supportedVersions` `["2026-07-28"]` alone, not the legacy revisions, because a client picks one of these for its stateless requests and no legacy revision has a stateless form (D-05); `capabilities` `{"tools":{}}`, the same object `initialize` answers; `ttlMs` `0` and `cacheScope` `"private"` (D-06); plus the `resultType` and `_meta` serverInfo that Task 1 puts on every result. No `instructions` key, because anything there sits in every session's context and the tool descriptions already say what each tool returns. Unknown methods still get `-32601`. `initialize`, `PROTOCOL_VERSIONS` and `DEFAULT_PROTOCOL_VERSION` do not change: 2026-07-28 is offered through `server/discover` because the revision has no `initialize`, and an `initialize` asking for it keeps being answered `2025-06-18` (D-08). Rewrite the doc comment on `PROTOCOL_VERSIONS` so it stops saying MCP 2 is left out and says instead that 2026-07-28 is not in this list because the revision has no `initialize` and is offered through `server/discover` (D-10); the `2025-03-26` paragraph of that comment stays. The deny list stands: reading `_meta` from a client-sent value must not be able to panic.
