# Phase 6: Archive - Context

Gathered: 2026-10-23

## Scope boundary

In: A tree-pass step that fills a NULL `session_meta.continues_from` once the predecessor is archived, so ingest order no longer loses the link (#11). Retention checks again, just before each session's delete, that the transcript at its stored path is still gone, and reports a session it keeps as a note; `retention::apply::delete_session` clears derived rows through `reindex::clear_derived`, so the derived-table delete list exists once (#43, with the 2026-10-22 simplify review's finding). The observe entity query driven from the session's turns, in both `observations regenerate` and the ordinary pass, with a test that fails if its plan goes back to the kind index (#70). The doc comments that state the old behaviour rewritten.
Out: A one-off repair of existing stores' links. Linking from `terminus backfill` or `terminus ingest <path>` before the next tree pass. Any new index or `DERIVED_SCHEMA` bump. Any change to `show`, the MCP tools or `cmd/observations.rs`. Reworking `from_blob` or `files()` in `observe/mechanical.rs`. Changes to the user docs, which already describe the fixed behaviour. Running `cargo fmt` over the workspace. The other open issues.
Deferred: None.
Plan shape: multiple plans, same phase (an estimated eight to ten tasks across three independent fixes, #11, #43 and #70, against `workflow.max_plan_tasks` 8).

## Durable decisions

- D-01 (Continuation links): The link is repaired by a sweep in the tree pass's post-walk steps (`Tree::after_walk`), which picks sessions whose `continues_from` is NULL and resolves each one's first-turn `parent_uuid` through `turns` by the same rules as `ingest::continues_from`. A link that `terminus backfill` or `terminus ingest <path>` misses is filled on the next tree pass. Rejected: a per-file lookup in `apply`, which with no index on `parent_uuid` costs every committed file a store-wide probe (9.3 ms over 3,448 sessions on John's snapshot, 2026-10-23, so about 30 s on a 3,500-file backfill); a new partial index `turns(parent_uuid) WHERE turn_seq = 0`, which bumps `DERIVED_SCHEMA` from 5 to 6 and rebuilds every store; running it in `reindex`, whose module doc says `sessions` and `session_meta` are never touched; and running it in `driver::drive` for every walk, which reopens phase 5's rule that only the tree pass runs post-walk steps. Evidence: `crates/terminus-core/src/ingest/mod.rs` (`continues_from`, `apply`), `crates/terminus-core/src/store/schema.rs` (`idx_turns_uuid`, no `parent_uuid` index), `crates/terminus-core/src/reindex.rs` (module doc), `crates/terminus-core/src/ingest/driver.rs` (`Walk`), `crates/terminus-core/src/ingest/pass.rs` (`Tree::after_walk`), `.planning/phases/5/CONTEXT.md`.
- D-02 (Observe query): #70 is fixed by the shape of the query in `mechanical::entity_values` alone: it starts from `turns` by `session_key` and forces that join order (`turns t CROSS JOIN entities e` or `+e.kind`), with no new index and no `DERIVED_SCHEMA` bump, so no existing store rebuilds. The `e.turn_id IN (SELECT id FROM turns WHERE session_key = ?1)` shape `clear_derived` uses is not used, because with the `e.kind = ?` filter it still plans on `idx_entities_lookup`. Measured 2026-10-23 on John's snapshot (3,448 sessions, 138,371 `tool` entities): the current query plans `SEARCH e USING INDEX idx_entities_lookup (kind=?)`, both forced shapes plan `sqlite_autoindex_turns_1 (session_key=?)` then `idx_entities_turn (turn_id=?)`, and over 30 sessions the time fell from 1.82 s to 0.011 s with the same 86 values. Evidence: `crates/terminus-core/src/observe/mechanical.rs` (`entity_values`), `crates/terminus-core/src/store/schema.rs` (`idx_entities_lookup`, `idx_entities_turn`, the note that an index reaches a store only through a `DERIVED_SCHEMA` bump), `crates/terminus-core/src/store/open.rs` (`DERIVED_SCHEMA = 5`), `crates/terminus-core/src/reindex.rs` (`clear_derived`).

## Decisions

- D-03 (Continuation links): The fix writes `session_meta.continues_from` itself, and `show` and the MCP tools do not change, because both read the column through `recall::context::window`. Evidence: `crates/terminus-core/src/recall/context.rs` (`window`), `crates/terminus/src/cmd/show.rs` (`render_window`, `window_value`), `crates/terminus/src/cmd/mcp/tools.rs` (`run_context`).
- D-04 (Continuation links): No one-off repair of existing stores. Measured 2026-10-23 on John's snapshot: of 3,153 sessions with a NULL link, none would resolve today; on disk, of 1,810 top-level transcripts, none depends on the `parentUuid` fallback. A NULL-only sweep heals any older miss anyway. Evidence: `~/.local/share/terminus/snapshots/terminus-20261023T135008.648Z.db` (opened read-only), `~/.claude/projects`.
- D-05 (Continuation links): The lineage rules do not change: a foreign `session_id` wins over the fallback, only the first turn's `parentUuid` names a predecessor, a session never links to itself (a sidecar resolving to its parent's id included), and a link already set is never overwritten, since the sweep fills only NULLs, as `write_session_meta`'s `coalesce` does. Evidence: `crates/terminus-core/src/lineage.rs` (`foreign_predecessor`, `is_self_link`), `crates/terminus-core/src/ingest/mod.rs` (`write_session_meta`), `crates/terminus-core/tests/lineage.rs`.
- D-06 (Continuation links): The proof runs two real tree passes through `pass::run_with` in `crates/terminus-core/tests/lineage.rs`: the first sees only the later session, whose first record carries `parentUuid`; the second sees its predecessor too. It mirrors `a_sidecar_ingested_before_its_parent_records_the_same_key`. Evidence: `crates/terminus-core/tests/lineage.rs` (`Tree::pass`).
- D-07 (Retention): Just before each session's delete, `apply` reads that session's `session_meta.transcript_path` again and runs the same `transcript_is_gone` test, where only `NotFound` counts as gone. The stored path is used rather than the session key, because after a moved `.claude` directory the key names a path that is gone. `Selection.delete` keeps carrying keys only, so the hand-built selections in the tests do not change. Evidence: `crates/terminus-core/src/retention/mod.rs` (`transcript_is_gone`, `Selection`), `crates/terminus-core/src/ingest/mod.rs` (`apply`'s moved-file `UPDATE session_meta SET transcript_path`), `crates/terminus-core/tests/retention.rs` (`a_moved_claude_dir_keeps_every_session_whose_transcript_is_still_on_disk`).
- D-08 (Retention): The check runs per session, inside the loop of one transaction per session, not once at the top of `apply`, so a transcript that comes back partway through a batch of up to 100 is still caught. It narrows the window and cannot close it, since the ingest lock guards the store, not the transcript tree. Evidence: `crates/terminus-core/src/retention/apply.rs` (`apply`, `delete_one`, `MAX_PER_PASS`), `crates/terminus-core/src/ingest/driver.rs`.
- D-09 (Retention): A session the check keeps is counted and reported in `runs.notes` through `Applied::notes()`, never in the list that feeds `runs.error` and never in `deleted`, so a healthy pass stays clean in `status` and `doctor`. Evidence: `crates/terminus-core/src/retention/apply.rs` (`Applied::errors`, `Applied::notes`, `is_silent`), `crates/terminus-core/src/retention/mod.rs` (`Selection.excluded`), `.planning/phases/5/CONTEXT.md` (the #96 split between errors and notes).
- D-10 (Retention): The re-check is proved in `crates/terminus-core/tests/retention.rs` on a real archived fixture: archive it, make it eligible (planting `is_final` and an old `last_turn_at`, which `evaluate` reads, as setup only), remove the transcript, run `retention::evaluate`, write the transcript back, run `retention::apply` with that selection, and assert the session's rows are unchanged and nothing was deleted. Evidence: `crates/terminus-core/tests/retention.rs` (`Bench::archive`, `rows`, `remove_transcript`, `delete_names_only_a_session_whose_transcript_is_gone`).
- D-11 (Retention): `delete_session` calls `reindex::clear_derived` for `paths`, `entities`, `compactions`, `turns_fts` and `turns`, then deletes `observations`, `session_meta`, the block rows, `sessions` and the watermark itself. `clear_derived` becomes `pub(crate)`, its doc names both callers, and `delete_one`'s "Child first" paragraph points to it instead of restating the list. Evidence: `crates/terminus-core/src/retention/apply.rs:180-206` and `crates/terminus-core/src/reindex.rs:239-251` (the same five statements in the same order), the bundled SQLite's `SQLITE_DEFAULT_FOREIGN_KEYS=1`.
- D-12 (Retention): The existing deletion tests, which count every derived table and `turns_fts` through `matches`, are the proof for D-11, and no new test is added. Evidence: `crates/terminus-core/tests/retention.rs` (`a_deletion_removes_every_row_the_session_owns`, `a_failure_on_one_session_does_not_stop_the_next`, `Bench::rows`, `Bench::matches`).
- D-13 (Observe query): One change covers both callers, because `observe_new` (through `write_one`) and `regenerate` (through `rewrite_one`) reach `entity_values` only through `mechanical::observe`, so neither `observe/mod.rs` nor `cmd/observations.rs` changes. Evidence: `crates/terminus-core/src/observe/mod.rs`, `crates/terminus-core/src/observe/mechanical.rs` (`observe`).
- D-14 (Observe query): The output stays identical: the same DISTINCT `value_norm` values in the same `ORDER BY e.value_norm` order, because `cap` keeps the first `MAX_LIST` (64) in that order and `regenerate` rewrites stored documents. Measured 2026-10-23 on John's snapshot: the ordered output matched between the two shapes on all 10 tool and error lists of the 5 sessions with the most distinct values. Evidence: `crates/terminus-core/src/observe/mechanical.rs` (`MAX_LIST`, `cap`), `crates/terminus-core/tests/observe.rs`.
- D-15 (Observe query): `from_blob` and `files()` stay out of this phase; #70's 2026-10-22 comment and roadmap criterion 4 name only the entity query, and `files()` already drives from `turns`. Evidence: #70, `.planning/ROADMAP.md` (phase 6 criterion 4), `crates/terminus-core/src/observe/mechanical.rs`.
- D-16 (Observe query): The guard test runs EXPLAIN QUERY PLAN on the exact SQL `entity_values` executes, shared as a constant and not copied into the test, on a store built from `CREATE_SQL` in a temporary directory, and asserts the plan uses `idx_entities_turn` and never `idx_entities_lookup`. It asserts only index names from the schema, not SQLite's plan wording, so a SQLite rewording on a rusqlite bump cannot fail it. John chose this over counting VM steps and over matching the full plan text. No `ANALYZE` or `sqlite_stat1` exists in the crates or the snapshot, and an empty store gives the same plans as the snapshot. Evidence: `crates/terminus-core/src/observe/mechanical.rs`, `crates/terminus-core/src/store/schema.rs` (`CREATE_SQL`), `Cargo.lock` (rusqlite 0.40.2, bundled SQLite 3.53.2).
- D-17 (Comments and docs): New comments and tests cite only `#11`, `#43` and `#70`, never a requirement id or a decision tag, and comments are rewrapped by hand with no `cargo fmt` over the workspace. The doc comments that state the old behaviour change with the code: `continues_from`'s doc in `ingest/mod.rs`, `clear_derived`'s doc and the module doc in `reindex.rs`, `delete_one`'s doc in `retention/apply.rs`, the `Delete` arm in `retention/mod.rs`, and `entity_values`'s doc in `observe/mechanical.rs`. `docs/design/0004-archive-and-block-rows.md`, `docs/json-shapes.md` and `docs/configuration.md` already describe the fixed behaviour and do not change. Evidence: `crates/terminus-core/tests/planning_tags.rs`, those files.
