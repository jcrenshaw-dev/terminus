# Phase 3: Owner-only files - Context

Gathered: 2026-10-18
Feeds: /cad-plan 3

## Scope boundary

In: Every temporary that install and uninstall create is 0600 from the moment it is opened: the `settings.json` rewrite, the backup, uninstall's two writes and the stored version file's temporary. A `settings.json` Terminus creates is 0600 (INST-15, #64). `terminus data move` refuses an existing destination that is a symlink, is owned by another uid, has group or world bits, or cannot be listed, and runs the same check again after the confirmation (STOR-12, #59). The regression tests for both fixes, the docs that describe them, and a reading of the installed Claude Code bundle for the mode it writes `settings.json` with.
Out: Any change to `Store::open` or `open_read_only` (D-01). `export`'s destination check (D-14). The owner and mode of the destination's parent directory, and of a missing settings directory (D-05, D-09). Narrowing a group- or world-readable destination instead of refusing it (D-10). Adding `libc` (D-13). Session keys (phase 4) and terminal output escaping (phase 5).
Deferred: None.
Plan shape: multiple plans, same phase. `/cad-plan` breaks it down, likely one plan for #64 and one for #59, with the docs.

## Durable decisions

- D-01 (Store::open): `Store::open` does not change in this phase. `tighten` keeps ignoring a failed chmod (store D-12), and no open refuses a store another uid owns. The gap is recorded in `THREAT-MODEL.md`: a store reached through `TERMINUS_DATA_DIR` or an older pointer to another account's directory is not checked for its owner. A refusal in `Store::open` alone would stop the hook-spawned ingest from writing into a foreign store, but not recall or injection from reading planted turns, because both open read-only. It would also stop a group-shared or root-created store that ingests today, and on the hook path nobody would hear about it until `status` or `verify` ran. This phase closes `data move`, the main way into a foreign store. Refusing in every open, and refusing behind a switch that defaults off, were both considered and left out. Evidence: `crates/terminus-core/src/store/open.rs:411-430`, `:484-497`, `:137-160`, `:866-870`; `crates/terminus-core/src/inject/mod.rs:129-130`; `crates/terminus/src/cmd/read.rs:97`; `crates/terminus-core/src/ingest/pass.rs:172-177`; `crates/terminus/src/cmd/status.rs:40`; `crates/terminus/src/cmd/verify.rs:12`; `THREAT-MODEL.md:67`.

## Decisions

- D-02 (Temporaries): The fix goes in `create_temporary`, which opens through `terminus_core::owner_only::options()`. That one change covers every caller: the settings rewrite (`json_file.rs:666`), the backup (`json_file.rs:478`), and uninstall's `apply` and `overwrite` (`uninstall.rs:157`, `:216`), all through `write_atomically`/`create_temporary`. The stored version file (`binary.rs:273`) also goes through it and keeps its final 0755, because `copy_into` sets that mode before the rename (`binary.rs:366`). Fixing each call site separately would leave uninstall's `overwrite` or a future caller at the umask mode. Evidence: `crates/terminus/src/cmd/install/mod.rs:41-67`; `crates/terminus/src/cmd/install/json_file.rs:478`, `:652-679`; `crates/terminus/src/cmd/install/binary.rs:273`, `:355-379`; `crates/terminus/src/cmd/uninstall.rs:157`, `:216`; `crates/terminus-core/src/owner_only.rs:59-75`; `crates/terminus/tests/install.rs:414-418`.
- D-03 (Rewrite mode): A `settings.json` that already exists keeps its own mode. The temporary starts at 0600, and the target's mode is copied onto it after the write only when it differs. A 0600 file is never wider than 0600 at any moment, and a file the user made 0644 stays 0644. Narrowing every rewrite to 0600 would silently change the mode of a file the user owns and chose. Evidence: `crates/terminus/src/cmd/install/json_file.rs:694-698`; `audit/claude-security.md:155`.
- D-04 (Backup mode): The backup is created 0600 and stays 0600 whatever the source's mode, because it is Terminus's own file. Today `copy_through` copies the source's mode ("permissions and all"), and its docstring changes with it. Uninstall writes back the backup's bytes, not its mode: `overwrite` goes through `fill`, which takes the live file's mode. Evidence: `crates/terminus/src/cmd/install/json_file.rs:702-725`, `:516-518`, `:1195-1207`; `crates/terminus/src/cmd/uninstall.rs:216`.
- D-05 (Fresh settings.json): A `settings.json` Terminus creates is 0600 because the temporary is created 0600, since `fill` finds no target to copy a mode from. A settings directory that `write_atomically` creates stays at `std::fs::create_dir_all`'s umask default, because it is Claude Code's directory and owner-only D-04 narrows only Terminus's own leaf. Evidence: `crates/terminus/src/cmd/install/json_file.rs:657-659`, `:696`; `crates/terminus-core/src/owner_only.rs:25-40`.
- D-06 (#64 regression): The regression has two parts. The shipped binary runs under an explicit `umask 022` spawn, the `UMASK_022` pattern in `tests/owner_only.rs`, and a fresh `settings.json` must come out 0600; it is 0644 before the fix. A unit test at `create_temporary` checks the opened file's mode, and skips with a printed reason when the umask is already 077, so it cannot pass on the commit before the fix. Both parts are needed because a 0600 target ends up 0600 before and after the fix, so the binary boundary cannot see the window. Evidence: `crates/terminus/tests/owner_only.rs:1-10`, `:98-103`; `install.sh:237`; `crates/terminus-core/tests/discover.rs:247-262`; `.planning/phases/2/CONTEXT.md:39`.
- D-07 (Destination rule): An existing destination passes only when `symlink_metadata` shows a real directory, not a symlink, owned by this uid, with `mode & 0o077 == 0`, that can be listed and is empty. A destination that does not exist (`NotFound`) is still accepted and created 0700. Any other error refuses before the question is asked, including a list failure (EACCES) and a file where the directory should be (ENOTDIR). Today `unwrap_or(false)` counts a directory it cannot list as empty. Evidence: `crates/terminus/src/cmd/data.rs:197-221`, `:306`; `crates/terminus-core/src/owner_only.rs:52-56`; `docs/commands.md:152`; `.planning/REQUIREMENTS.md:31`; `audit/claude-security.md:57`.
- D-08 (Path normalization): The destination is normalized before the symlink check: trailing slashes and `.` parts are dropped, because `symlink_metadata` on `link/` follows the link. The check and the pointer use the same normalized path. Measured 2026-10-18 with rustc 1.99.0 on Linux: `symlink_metadata("…/link")` gives `is_symlink=true`, `"…/link/"` gives `is_symlink=false is_dir=true`, and `PathBuf::from("/cwd").join("rel/")` keeps the slash. Evidence: `crates/terminus/src/cmd/data.rs:278-289`.
- D-09 (Symlinked parents): Only the last part of the path is checked for a symlink, so symlinked parent folders are accepted. The parent's owner and permissions are not checked. `THREAT-MODEL.md` records the gap: a parent another account can write to, without the sticky bit, lets that account rename the checked directory away after the copy. Refusing any symlinked parent would refuse every destination under `/var/folders` on the macOS runners, and setups like `~/.claude -> /data/.claude`. Evidence: `CHANGELOG.md` `[Unreleased]` (CI on `macos-15` and `macos-15-intel`); `crates/terminus-core/src/owner_only.rs:25-34`; `audit/claude-security.md:52-55`; `THREAT-MODEL.md:107`.
- D-10 (Wide destination): An empty directory the user owns that has group or world bits is refused, and the message carries the `chmod 700` command. Terminus does not narrow it, because it narrows what it creates and nothing it merely found. "Group or world bits" means `mode & 0o077`, so an inherited setgid bit does not count. This changes behavior: under umask 022, `mkdir ~/newstore` followed by `data move ~/newstore` is refused where v0.1.1 moved the store. STOR-12 asks for this refusal. Evidence: `crates/terminus/src/cmd/export.rs:160-167`; `crates/terminus/src/cmd/doctor.rs:779`; `.planning/REQUIREMENTS.md:31`.
- D-11 (Second check): "Checks again after the confirmation" means D-07's rule runs a second time after the answer and the lock, right before `copy_tree` creates the folder. A destination that was absent at the first check and is present at the second is refused. Today `owner_only::create_dir_all` accepts a folder that already exists, which is the exploit #59 describes: the directory is created while the prompt waits. Evidence: `crates/terminus/src/cmd/data.rs:109-145`; `crates/terminus-core/src/owner_only.rs:54`; `audit/claude-security.md:50`.
- D-12 (#59 regression): The regression tests go in `crates/terminus/tests/datamove.rs`: a symlink destination, a 0777 directory, an unlistable 0300 directory the user owns (skipped with a printed reason under root), and the second check, which pipes stdin, waits for the question, creates the destination, then answers `y`. The other-uid case is tested through a seam that takes the expected uid, because a test that is not root cannot make a directory another uid owns that it can also list. A test against a real root-owned path such as `/` would be refused by the group-and-world rule first, and pass with the uid check missing. Evidence: `crates/terminus/tests/datamove.rs:348-398`; `crates/terminus-core/tests/discover.rs:247-262`; `crates/terminus/src/cmd/install/mod.rs:460-493`.
- D-13 (Own uid): `data move` learns its own uid from a probe file: it creates a new file, reads its owner and removes it. POSIX sets a new file's owner to the process's effective uid, so the answer is the same on Linux and macOS, with std alone. `owner_only.rs` keeps to std alone (owner-only D-01) for hook-path speed, and `data move` is not on the hook path. Adding `libc` for `geteuid` was rejected because it puts a new crate in the shipped binary on all four release targets. `fstat` on a pipe was rejected because POSIX does not specify a pipe's owner. Evidence: `crates/terminus-core/src/owner_only.rs:12-15`; no `getuid`/`geteuid` in `crates/`; `cargo tree --offline -p terminus -e normal --target <t> -i libc` prints nothing for the four targets in `.github/workflows/release.yml:25-34` (2026-10-18).
- D-14 (Export): `export`'s equally loose destination check stays as it is. STOR-12 names `data move` only, and a shared helper would refuse an export into the user's own empty 0755 directory, which works today. Evidence: `crates/terminus/src/cmd/export.rs:134-154`; `.planning/REQUIREMENTS.md:31`.
- D-15 (Claude Code's mode): The first plan reads the installed Claude Code bundle to learn what mode it gives `settings.json` when it rewrites it: whether it keeps the existing mode or writes 0644. It records what it finds, the way phase 1 D-07 read the bundle for the hook output, and `THREAT-MODEL.md` states it. This does not change Terminus's fix; it changes what the threat model can claim about how long a 0600 file stays 0600. Evidence: `.planning/phases/1/CONTEXT.md` (D-07).
- D-16 (Docs): The docs change in the same change as the code. In `THREAT-MODEL.md`: the temporary's mode and the backup's "same permission window" (`:91-92`), the `data move` destination checks, which are no longer only lexical (`:96`, `:107`, `:263`), and the gaps D-01 and D-09 leave. Also `docs/commands.md:152`, `docs/design/0004-archive-and-block-rows.md:288-290`, and a `CHANGELOG.md` `[Unreleased]` entry under `### Fixed`. `THREAT-MODEL.md:67` changes only to record D-01's gap. `SECURITY.md` describes neither behavior and stays as it is. Evidence: `.planning/phases/2/CONTEXT.md:31` (D-14); `THREAT-MODEL.md:67`, `:88-92`, `:96`, `:107`, `:263`; `docs/commands.md:150-152`; `docs/design/0004-archive-and-block-rows.md:286-290`; `SECURITY.md:23`; `CHANGELOG.md:10-35`.

## Acceptance criteria

- [ ] AC1: Under umask 022, `terminus install` into a config directory with no `settings.json` creates one at 0600.
- [ ] AC2: Every file `create_temporary` opens is 0600 the moment it is opened, before any byte is written. After install, an existing 0644 `settings.json` is still 0644, its backup is 0600, and the stored version file is 0755.
- [ ] AC3: `terminus data move <dest>` refuses before asking when the destination is a symlink (with or without a trailing slash), is owned by another uid, has any group or world bit, or cannot be listed, and the store and the pointer stay as they were. A destination that does not exist, or an empty 0700 directory this uid owns, is still accepted.
- [ ] AC4: When the destination is created or replaced while `move it? [y/N]` waits, answering `y` is refused and nothing is copied.
- [ ] AC5: Each fix's regression test fails on the commit before the fix and passes after it.
- [ ] AC6: `THREAT-MODEL.md` describes the temporary as created 0600, the `data move` destination checks, the unchecked parent directory, the unchecked owner of a store reached through `TERMINUS_DATA_DIR` or an older pointer, and the mode Claude Code writes `settings.json` with. `docs/commands.md` and `docs/design/0004-archive-and-block-rows.md` list the new refusals, and `CHANGELOG.md` `[Unreleased]` carries #64 and #59.
- [ ] AC7: The pull request that lands this phase carries `Fixes #64` and `Fixes #59`, and both close once it merges. (human-verify: needs GitHub, after landing)

## Flagged assumptions

- Claude Code keeps an existing `settings.json`'s mode when it rewrites the file - Unclear, D-15 has the first plan check it; if wrong: the 0600 file Terminus creates goes to 0644 on Claude Code's next write, and `THREAT-MODEL.md` has to say so.
- A probe file's owner is the effective uid on every release target - Likely, POSIX requires it for `open` with `O_CREAT`, and Linux uses the fsuid, which equals the euid unless `setfsuid` was called; if wrong: `data move` refuses every existing destination on that platform, or accepts every one.
- Where the probe file is created is the planner's call - Likely, it has to be a directory this process can write to and owns; if wrong: the probe fails and `data move` refuses where it should not.
- The `create_temporary` unit test's 077-umask skip is enough to keep it from passing on the old code - Likely; if wrong: a developer or CI umask of 077 makes the test pass before the fix and AC5 is not shown for it.
